# Design proposal: Getty ESP web upload via local bridge

Date: 2026-10-29. **Proposed only, not implemented or validated against a contributor account.** Research and sources: `docs/archive/2026-10-29-getty-web-automation/research.md`. Current implementation: `docs/current/sor/stock-upload.md`. This proposal does not change current contracts.

## Decision and boundaries

If Getty permits this specific automation, add an opt-in `Getty ESP web (local bridge)` target. The app previews selected committed exports; a local helper runs a dedicated automated browser and interacts with the Getty contributor UI. Default to a visible, user-controlled login using Getty credentials; automate navigation and file selection after authentication. A headless session is an optional capability only after real-account testing, not a promise. Without authorization, a supported runtime, a known page or a safe login, stop and offer existing manual staging/open-ESP flow. Prefer a Getty-supported API if available and authorized.

First release scope: creative illustration EPS+JPG pairs, one contributor account and one explicit batch, upload only. No auto-submit for inspection, no metadata application, no release upload, no bypass of CAPTCHA/MFA or anti-bot controls. Export a CSV for manual application if requested; never silently claim it was imported. Other formats and account types require separately validated adapters. Do not infer that generated artwork is permissible: require a user attestation against current Getty rules and block on known prohibited provenance; where unknown, surface the uncertainty and require review.

## User journey

1. In Upload, choose Getty web target, checked eligible rows and account/submission type. Preserve existing selection semantics and I-80. A preflight lists exact files and per-file size, proposed unique paired names, destination/account/type, total bytes, local helper, intended web upload (not submission), content-policy warning and metadata excluded. Unreadable, missing, duplicate or invalid pairs block affected rows with actionable reasons. Nothing is sent or opened merely by viewing preflight.
2. After explicit confirmation, app creates an immutable job and supplies **only** selected, approved bytes to the helper. Reuse the same naming/collision logic as `espstage.ts` rather than having two naming schemes. Remap both sides of each pair consistently; account for case-insensitive collisions. Preflight revalidation detects changed files before transfer. Show spool progress; until the helper acknowledges all bytes, closing the app may interrupt transfer.
3. Helper starts an isolated browser at the confirmed official HTTPS entry point. User enters their Getty username/password in Getty's own visible login form, and completes MFA/CAPTCHA manually. The helper never asks for an OTP or bypasses challenges. Show `Waiting for sign-in` in the app, with Open/Focus browser and Cancel. If the session expires, return to this step. Do not use the user's normal browser profile.
4. After verifying the signed-in account through a separately validated, non-sensitive page marker, navigate by tested page controls to Upload & review content, choose the confirmed type and create/select the confirmed batch. Create-batch click is a remote mutation, covered by the initial confirmation. Never guess selectors, account type or batch based only on historical examples. If ambiguous, change detected or account mismatch, stop for user action.
5. Select only manifest files through the observed input/chooser; upload in bounded chunks only if the tested UI supports it. Follow the portal's observed order and any server prompts. Monitor per-file completion/errors and the batch view; distinguish browser selection, bytes transferred and Getty-confirmed receipt. If Getty reports only aggregate success, show aggregate confirmed and per-file unknown rather than inventing per-file success.
6. Present batch link only after validating its origin; show received/failed/unknown files and a clear `Not submitted for review` label. User may open ESP to review metadata, releases and submit manually. Do not generate an uploaded badge from a local stage or a merely selected file.

## Credentials, sessions and safety

- **Default:** credential entry occurs directly in the helper's visible browser, not through app IPC, logs, URL, CLI or environment. The ephemeral dedicated profile is deleted when the job ends or the helper exits. Restart requires sign-in again. A background browser may be kept alive during an approved job only if supported; it is not unattended login across restarts.
- Optional later enhancement: user explicitly opts into a persistent, per-account dedicated profile outside the workspace, protected by OS user ACLs, not synced or committed, with Forget/Sign out and revocation instructions. Cookies and profile contents are credentials; OS encryption/ACL protection varies, so document residual same-user/malware risk. Lock to one process per profile. Before adding this, amend and test I-81 with a narrow, reviewed exception; never silently write auth state to disk.
- If product insists on automatic username/password entry, evaluate **only after permission and threat review**: explicit opt-in per run, existing browser vault, one-time authenticated local IPC, memory-only helper handling, fill only after exact HTTPS origin and validated login form, immediate discard, no credentials on redirects, no password/token logs, traces or screenshots. Never automate MFA, CAPTCHA or retry bad credentials. Manual entry is safer and is the recommended MVP.
- Helper must accept navigation only to a reviewed exact HTTPS origin/redirect allowlist, verified from the real login flow; no arbitrary URL supplied by a page or user job. TLS verification remains on. If login requires unapproved origins or download hosts, pause and review rather than widen automatically. Browser page content is untrusted; don't expose privileged Node APIs to it.
