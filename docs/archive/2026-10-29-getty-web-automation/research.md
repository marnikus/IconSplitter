# Getty contributor web upload: research (2026-10-29)

Status: research and proposed design only; no implementation or Getty account test. See `docs/archive/2026-10-29-getty-web-automation/design.md`. Current behavior is in `docs/current/sor/stock-upload.md` and wins over this proposal.

## Scope and evidence

Goal: from IconSplitter, explicitly select exported files and upload them through the contributor web page, using the contributor's credentials, with as much work in the background as practical. Upload is not final submission for inspection. This research used public documentation and repository inspection; it did **not** access an authenticated Getty page, test selectors, verify Getty account permissions, or send files. Outbound sandbox network access is restricted; public web search was used for external sources. Claims from third parties are labeled accordingly and might be outdated.

| Finding | Evidence and implication |
| --- | --- |
| Getty ESP is a batch-oriented contributor workflow | A [2018 walkthrough](https://specialistpractices.wordpress.com/2018/10/19/becoming-a-getty-or-istock-contributor-and-uploading-your-first-image/) describes My Content → Upload & review content → select type → New submission → upload. A [more recent third-party guide](https://www.metaextractor.com/help/getty) describes Create Batch, uploading, then Templates → Upload and Apply. Labels, order, availability, regions, and confirmation differ by account and can change. These are hypotheses, not verified selectors. |
| Vector preparation matters | [Getty's Preparing Your Content](https://contributors.gettyimages.com/article/9146) says CS6-compatible EPS, paired RGB JPEG with the same basename, minimum 1900 × 2800 px and recommends 4075 × 4075 px. It says generative-model submissions are not accepted. Confirm the current contributor policy and account-specific rules at implementation time; do not infer source provenance from file type. |
| Metadata and submission are separate | [DeepMeta 4's guide](https://deepmeta.creativ.zone/blog/post/deepmeta-uploads) describes a batch, upload, CSV import and separate submission; its CSV can be selected with assets. For ESP itself, [PhotoKeyworder](https://blog.photokeyworder.ai/2024/11/16/visualmind-ai-automated-istock-keywords-disambiguation/) describes applying CSV after video upload. Do not assume the ESP page accepts CSV alongside images, or that importing metadata means submitting. Validate the existing CSV and format against the user's current ESP account. |
| Credentials can be used through an interactive login | [DeepMeta's login guide](https://www.deepmeta.com/3/userguide/login) describes Getty credentials entered in a browser authorization flow for DeepMeta; this does not prove that our app has authorization or API access. [Playwright authentication](https://playwright.dev/docs/auth) explains browser state reuse and warns that stored state can impersonate the account. MFA and expiring sessions require user intervention. |
| Browser-only app cannot generally operate Getty's page | [MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage) restricts cross-origin DOM access; `postMessage` works only with cooperation from the other page. [MDN file input](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file) says scripts cannot set a file-picker value to a local path. Opening an ESP tab or using a web worker does not grant control of its login or picker. Direct API requests also require the provider's CORS and authorization support. |
| A local automated browser is technically plausible, not established for Getty | [Playwright file input](https://playwright.dev/docs/input#upload-files) supports `setInputFiles` and file chooser handling, including multiple files. This does not establish how the actual ESP uploader is implemented, whether the page accepts automation/headless, or whether the workflow is permitted. A visible browser remains necessary for user challenges. |
| An API is a distinct option, not proof of web access | [Getty developer documentation](https://developer.gettyimages.com/docs/) documents API-key and OAuth authentication for its API; it does not establish public contributor upload rights. The historical third-party [ESP SDK](https://pkg.go.dev/github.com/dysolution/espsdk) refers to API keys and a sandbox, but is not evidence of current endpoint availability or approval terms. The repository has an `esp-https` path; its real account eligibility and operation remain unverified here. |
| Automation permission is unresolved | [Getty site terms](https://www.gettyimages.com/company/terms) prohibit data mining, robots or similar data gathering or extraction methods. Applicability to ESP upload automation and the user's contributor agreement is not established by this wording. Obtain Getty's written clarification/authorization for the intended workflow before shipping or using browser automation; do not interpret another product's existence as permission. |

## Existing app and important gaps

- `src/lib/stockupload/discovery.ts` restricts selections to existing committed `export.json` outputs (I-80). `src/lib/stockupload/plan.ts` builds the upload plan; existing preflight must remain the source of selection and validation.
- `src/stockupload/espstage.ts` makes a flat non-overwriting batch with collision-safe names and CSV. This is local staging, not network delivery. `src/stockupload/runupload.ts` currently records staging through the same per-task result path that assigns badges/status; the new design must **not** mistake staged/badged files for remote confirmation. Fix/migrate semantics if implementing; do not silently reinterpret old history.
- `tools/bridge/server.mjs` serves a loopback-only helper, with existing FTPS/SFTP/ESP routes and local-origin CORS. `src/lib/stockupload/bridgeclient.ts` transfers bytes to it. Existing origin checks and open endpoints are not by themselves a sufficient authorization design for a browser-controlling, file-reading helper. Harden and test independently.
- `src/lib/stockupload/credvault.ts` holds stored stock credentials in IndexedDB or a session fallback (I-81). Those credentials are not a Getty login session. A bridge browser profile is a different sensitive store and conflicts with an unqualified reading of I-81 unless the contract is explicitly reviewed and updated. The default proposed mode uses an ephemeral profile instead.
- `package.json` has no Playwright runtime dependency or browser distribution. A future change needs an explicit version, installation/update strategy, license review and Windows packaging/support plan. Do not assume the user's existing browser profile can safely be controlled.

## Evidence still required before implementation

1. Getty permission and applicable terms; accepted contributor account, permitted submission type and a safe test batch. Never ask users to put credentials in chat or issue logs.
2. With explicit account-owner participation, inspect current login redirects, MFA, page labels, batch selection, chooser, upload states, association of EPS/JPG and durable per-file acknowledgments. Capture only sanitized observations, no account identifiers, cookies or image content.
3. Determine current size/count limits, batching, metadata format and timing, and allowed content provenance from Getty's current account-specific guidance. In particular, IconSplitter's AI-related features make the no-generative-model rule a material preflight question.
4. Test whether a dedicated browser works headfully, then whether the same approved flow works headlessly and across restart. Confirm interaction requirements and expiry; if it fails, use visible mode or manual staging, not anti-detection workarounds.
5. Check a supported API/partner route with Getty before relying on it. If authorized and adequate, prefer the supported route over brittle page automation; otherwise manual staging remains usable.
