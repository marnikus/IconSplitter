# Large-list selection response — plan before implementation

## Problem and target
Select all/deselect all freezes review lists above 100–1000 images. Target: at least 80% lower interaction response time (after <=20% of before), measured on the same 100/1000-item fixtures and runtime. Four checkable list tabs: Batch, Selection V2, Generate SVG, SVG to upload. Sheets has no image-list select-all surface; do not invent one.

## Architecture diagnosis
- Selection V2 passes the whole changing list-props object into every row. SVG/Upload similarly pass action bags containing the entire checked array/active id. Every checkbox update traverses all thumbnail, metadata, status, button and preview subtrees again.
- SVG thumbnails rebuild/parse previews on rerender; Upload recomputes effective settings and preview presentation. Checkbox membership uses `includes` inside each row, producing quadratic work for select-all.
- Batch mirrors checked ids to `row.selected` for processing compatibility. Its sync effect calls `isRowSelected(rows, id)` (a whole-list find) from two whole-list filters. Every changed selected flag also invalidates expensive row content. Existing Batch memo comparison ignores event freshness and several file attributes.
- Shared deselect-visible also uses nested `includes`; SVG affected-count derivation has the same quadratic pattern.

## Steps
1. Add a reproducible benchmark over the actual four list components, real preview code and representative SVGs, at 100 and 1000 rows. Measure select/deselect/toggle commits before changing production. Prefer actual headless Chromium interaction-to-next-painted-frame measurements; keep setup/scan/mount separate and record methodology/limits. Keep browser tooling outside project dependencies.
2. Add failing regressions for selection-only presentation work, callback freshness, data/preview invalidation, and linear Batch reconciliation; preserve all existing behavioural assertions.
3. Introduce a shared stable presentation-props boundary: current committed callbacks forward through stable event bridges; ordinary data remains reactive. Keep checked/active booleans outside memoized row contents. Each list builds one Set for membership, not one search per row. No deferred fake selection, hidden rows, DOM-only selection state, or virtualization that drops rows/controls.
4. Split lightweight row selection shells from memoized expensive content across all four lists. Batch keeps its processing mirror but computes check/uncheck differences in one indexed pass; compare every non-selection row property so source/status/dimension changes cannot become stale.
5. Make shared deselect-visible and SVG affected-count linear. Preserve order, hidden checks, active/anchor separation, case rules, eligibility, confirmation, history/session persistence and actual preview/export algorithms.
6. Rerun identical benchmark; report per-tab/sample medians and percent reductions, not a blanket claim unsupported by measurements. Iterate if 80% is not met. Keep deterministic work/invalidation regressions; do not weaken timing alarms or instrumented coverage rules.
7. Focused all-tab selection/history/preview tests, types/lint/quality, fast/full gates. Document contracts/results, append measured quality ledger without reading it, commit/push the current branch.

## Acceptance

Changed source/settings/zoom/background/versions/status and newly supplied event handlers remain live. One changed gesture remains one undo entry; no provider call or disk artwork change on selection. Existing shortcuts, filters and pending-row navigation remain unchanged.

## Second iteration plan (after first measurements, before implementation)
Production-mode measurements confirm content memoization alone does not reach the target everywhere: at 1000 rows, commit reductions are about 75–77% for Batch/V2/Upload, and frame delays remain high. Row CSS starts a background transition on every selected row, creating up to 1000 simultaneous animations. Even a minimal React shell still reconciles 1000 controlled checkbox subtrees.

Next: retain React/store checked arrays as the only selection state, but give each mounted list a shared layout-effect projection registry for native checkbox properties and the existing `.selected` classes. A bulk change projects the canonical committed snapshot in one indexed pass, before paint; memoized row shells no longer receive the checked array/booleans. Mount/data-change registration reapplies the snapshot, so React class updates and newly filtered rows stay consistent. This is a DOM presentation adapter, not DOM-only selection state: every action/history/count remains driven by the same React/store values. Native changes are routed through existing handlers. Add regressions for mount/unmount, selected data updates, hidden/remounted rows and snapshot restoration. Also remove background-colour row transitions (keep zoom sizing behaviour), so check-all doesn't launch 1000 highlight animations. No virtualization, hidden controls, delayed/chunked selection or new persistence.
